Decisões resolvidas

Fechadas em 2026-05-14 antes da Fase B. As três últimas são herdadas da Decisão #8 do PLAN.md (escopo de F8 desde sempre).

F8b-aMecânica: bloqueia o batch via asyncio.Event

Modal abre durante o upload. O generator SSE faz await event.wait(timeout=1800) num registry dict[nf_pending_id, asyncio.Event]. POST /resolve ou POST /cancel setam o event. Sem isso, timeout 30min trata como cancel.

F8b-bMúltiplos pendings: sequencial bloqueante

Cada pending = pausa do batch. Resolveu o pending atual → próximo PDF processa. Se virar pending também → modal reabre. Operador atravessa intercalando modais. UX previsível.

F8b-cTimeout 30 minutos

Por pending, não por batch. nf_pending.expires_at = created_at + 30min. Se expirar antes do resolve, mesmo efeito do cancel: NF descartada, fila restante cancelada.

F8b-dEscopo do cancel: PDF problemático + fila restante

Cancel mata o PDF problemático (upload_files.status = 'cancelado') e marca todos os arquivos ainda na fila como cancelado_pelo_lote. Arquivos já processados antes do pending permanecem em nf_entries. Sem rollback total.

F8b-eLayout do modal: PDF iframe + form ao lado

Split 2 colunas. Esquerda: <iframe src="/api/uploads/files/{id}/pdf"> reusa o endpoint F4 com sessão autenticada. Direita: prefilled (read-only) + missing fields (inputs required) + timer countdown + botões Salvar/Cancelar.

F8b-fBackfill NOT NULL: DELETE direto

Migration DELETE FROM nf_entries WHERE col_obrigatoria IS NULL OR col_obrigatoria = '' em cada uma das 11 colunas, antes do SET NOT NULL. Sem soft delete. Contagem registrada no log da migration para auditoria.

F8b-gGranularidade: NF inteira (herda Decisão #8)

Se qualquer produto da NF tem campo faltando, a NF inteira vai pra pending. Outros produtos da mesma NF não entram parcialmente em nf_entries. Mantém invariante "linha em nf_entries = NF completa".

F8b-h11 colunas viram NOT NULL (herda Decisão #8)

descricao, ncm, quant, preco_unitario, numero_nf, tipo_nota, data_emissao, cnpj, fornecedor, valor, contrato. Linha com qualquer um delas vazio é falha grave do parser e não pode entrar no banco — vira pending ou erro.

backend/app/pending_registry.py — novo módulo
# Registry global de events por nf_pending_id. Vida útil: do file_pending_input
# até resolve/cancel/timeout. Não persiste — se servidor reinicia, pendings ficam
# órfãos e job de startup marca como expirados.
import asyncio
from dataclasses import dataclass

@dataclass
class PendingDesfecho:
    resolved: bool = False
    cancelled: bool = False

_events: dict[str, asyncio.Event] = {}
_desfechos: dict[str, PendingDesfecho] = {}

def register(nf_pending_id: str) -> asyncio.Event:
    event = asyncio.Event()
    _events[nf_pending_id] = event
    _desfechos[nf_pending_id] = PendingDesfecho()
    return event

def signal_resolve(nf_pending_id: str) -> None:
    _desfechos[nf_pending_id].resolved = True
    _events[nf_pending_id].set()

def signal_cancel(nf_pending_id: str) -> None:
    _desfechos[nf_pending_id].cancelled = True
    _events[nf_pending_id].set()

def consume_desfecho(nf_pending_id: str) -> PendingDesfecho:
    return _desfechos.pop(nf_pending_id, PendingDesfecho())

05

Riscos & mitigações

ALTOSSE cai com modal aberto → Event órfão no registry

Cenário: usuário fecha aba, perde rede. Event no registry nunca é setado, generator nunca termina o request (mas o cliente já foi embora).
Mitigação: asyncio.wait_for com timeout 30min garante que o generator sempre termina. Job de startup do FastAPI varre nf_pending com status='aguardando' AND expires_at < now() e marca como expirados (recovery de orfãos cross-reboot).

MÉDIODELETE pré-F8 apaga histórico legítimo

Cenário: rows antigas com NULL eram dados úteis para o operador, e a migration as descarta sem possibilidade de recuperar.
Mitigação: migration imprime contagem deletada e SELECT pré-DELETE para o log do Alembic. Antes de rodar em produção, snapshot manual do banco. Se a contagem for surpreendente, dono pode rollback antes do SET NOT NULL.

MÉDIORace entre /resolve e timeout

Cenário: usuário clica Salvar exatamente quando o timeout dispara — dois sinais para o mesmo Event, dois UPDATEs no nf_pending.
Mitigação: endpoint /resolve valida status='aguardando' antes de processar (linha única, idempotente). Se já é 'expirado', retorna 409 e frontend mostra "Tempo esgotado, NF descartada".

BAIXOPDF iframe não renderiza no navegador (caching, CORS)

Cenário: alguns navegadores bloqueiam PDF inline em iframe. /api/uploads/files/{id}/pdf da F4 já manda Content-Disposition: inline, mas usuário pode ter PDF viewer desabilitado.
Mitigação: fallback button "Abrir PDF em nova aba" ao lado do iframe — se o iframe renderiza vazio, usuário ainda consegue ver o documento.

BAIXOMúltiplas abas do mesmo usuário tentando resolver o mesmo pending

Cenário: operador abre 2 abas com o batch, modal aparece em ambas.
Mitigação: idempotência do endpoint (mesma checagem status='aguardando'). Segunda aba recebe 409 e modal fecha com "Já resolvido em outra sessão".
