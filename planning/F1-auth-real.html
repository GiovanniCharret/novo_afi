00

Decisões já resolvidas

As 3 decisões do PLAN.md relevantes para F1 já foram resolvidas. Não rediscutir.

✓ Decisão #1 — SMTP via Hostinger inicial

Server smtp.hostinger.com, porta 587 STARTTLS, autenticação via env SMTP_USER/PASSWORD/FROM. Pré-requisito de produção: SPF + DKIM + DMARC configurados no DNS antes do primeiro envio. Sem isso, e-mails caem em spam.

✓ Decisão #2 — bcrypt cost 10, multi-scheme via passlib

Hash com passlib[bcrypt] cost 10. CryptContext(schemes=["argon2","bcrypt"], deprecated="auto") em backend/app/security.py permite migração automática para argon2id no login se a instituição mudar de algoritmo. Esqueleto já existe.

✓ Decisão #5 — Login por e-mail (sem username)

Cadastro {email, password}. Senha ≥10 caracteres, sem regras de complexidade obrigatórias (OWASP 2024 / NIST SP 800-63B). Truncamento bcrypt em 72 bytes documentado no endpoint de registro. users.username vira nullable=True só para preservar o seed legado em APP_ENV=development.

02

Fluxo de dados

Registro → e-mail → confirm → login. Token é gerado pelo backend, enviado no e-mail em texto claro, e armazenado como SHA256 hash no DB — interceptar o DB não permite forjar confirmações.

Token raw sai do servidor uma vez (no corpo do e-mail) e nunca persiste; só o sha256 fica em DB. Se o backend for comprometido, o atacante NÃO consegue forjar confirmações.

04

Código-chave

As duas peças onde dá pra errar feio: a geração e a verificação de token (precisam usar comparação constant-time), e a política de erros de login (não vazar se um e-mail existe ou não).

backend/app/security.py — token util
import hashlib, secrets, uuid
from datetime import datetime, timedelta, timezone

def generate_token() -> tuple[str, str]:
    """Retorna (raw, hash). Raw vai no e-mail, hash no DB."""
    raw = uuid.uuid4().hex  # 32 chars hex, 122 bits
    h = hashlib.sha256(raw.encode()).hexdigest()
    return raw, h

def verify_token(raw: str, stored_hash: str) -> bool:
    """Constant-time. Evita timing attacks que distinguem
    tokens parcialmente corretos."""
    h = hashlib.sha256(raw.encode()).hexdigest()
    return secrets.compare_digest(h, stored_hash)

def token_expiry(hours: int = 24) -> datetime:
    return datetime.now(timezone.utc) + timedelta(hours=hours)
backend/app/server.py — login + register
@app.post("/api/auth/register")
def register(p: RegisterPayload, db: DbSession):
    if db.scalar(select(User).where(User.email == p.email)):
        raise HTTPException(409, "E-mail já cadastrado")
    raw, token_hash = generate_token()
    user = User(
        email=p.email,
        password_hash=pwd_context.hash(p.password),
        confirmation_token_hash=token_hash,
        token_expires_at=token_expiry(24),
        email_confirmed=False,
    )
    db.add(user); db.commit()
    send_confirmation_email(p.email, raw)  # falha não rola back
    return {"ok": True, "message": "Verifique seu e-mail."}

@app.post("/api/auth/login")
def login(p: LoginPayload, request: Request, db: DbSession):
    user = db.scalar(select(User).where(User.email == p.email))
    # Mesma mensagem para e-mail inexistente E senha errada:
    # não vazar quais e-mails estão cadastrados.
    if not user or not pwd_context.verify(p.password, user.password_hash):
        raise HTTPException(401, "E-mail ou senha incorretos")
    if not user.email_confirmed:
        raise HTTPException(403, "Confirme seu e-mail antes de entrar")
    request.session["user"] = {"email": user.email, "id": user.id}
    return {"ok": True}

Riscos & mitigações

Risco
Sev
Mitigação
Vazamento de e-mails cadastrados — mensagens distintas para "e-mail não existe" vs "senha errada" permitem enumerar usuários.
HIGH
Resposta idêntica nos dois casos: 401 "E-mail ou senha incorretos". Idem no forgot-password: sempre retornar 200 sem revelar se o e-mail existe.
Token interceptado no DB (SQL injection, backup vazado, dump) permite forjar confirmação.
HIGH
DB armazena sha256(token), não o raw. Token raw só existe na memória do servidor durante o request e no corpo do e-mail. Atacante com acesso ao DB não consegue forjar.
Brute-force no login — atacante tenta milhares de senhas para uma conta.
HIGH
Bcrypt cost 10 já dá ~80ms por verificação — limita ~12 tentativas/s por core. Rate limiting (Questão #5) idealmente: 5 tentativas em 15 min por IP+email. Sem isso, atacante remoto ainda consegue ~1k tentativas/hora.
Timing attack no token compare — atacante mede tempo de resposta para descobrir tokens parcialmente corretos.
MED
secrets.compare_digest() faz comparação constant-time. Nunca usar == em comparações de token.
SMTP cai durante o registro — usuário fica sem o e-mail, conta criada mas inutilizável.
MED
Endpoint POST /api/auth/resend-confirmation permite reenviar. UI da tela "verifique seu e-mail" tem botão para isso. Falha de envio é loggada mas não faz rollback (questão #3).
Truncamento bcrypt em 72 bytes — senha de 80 caracteres tem só 72 verificados; UX ruim sem documentação.
LOW
UI do registro avisa: "senha entre 10 e 72 caracteres". Validação client + server. Limite raro de ser atingido na prática.
SPF/DKIM/DMARC ausentes no DNS → e-mails caem em spam → usuário acha que sistema está quebrado.
MED
Pré-requisito de produção bloqueia deploy (Decisão #1). Smoke da Fase D inclui validação via MXToolbox antes do go-live para usuários reais.
06

Perguntas abertas

✓ Resolvido — Política de senha: status quo (mínimo 10 chars, sem blocklist)
Senha ≥10 caracteres é a única validação. Sem blocklist de senhas comuns, sem zxcvbn, sem haveibeenpwned. Aceita "1234567890" se atender o tamanho — limitação consciente. Mais permissivo; trade-off explícito de UX vs segurança. Decisão tomada em 2026-05-13.
Decidido · 2026-05-13
✓ Resolvido — #1 Formato do token: uuid.uuid4()
Token gerado com uuid.uuid4().hex → 32 chars hex sem hyphens. 122 bits de entropia — astronomicamente forte. Frontend recebe o hex direto na URL do e-mail; backend compara via secrets.compare_digest. Confirmado em 2026-05-13.
Decidido · 2026-05-13
✓ Resolvido — #2 Storage do token: sha256 hash
DB armazena sha256(token) em confirmation_token_hash / reset_token_hash. Cliente recebe o token raw no corpo do e-mail; servidor compara hashes via secrets.compare_digest. Protege contra vazamento de DB dump. Confirmado em 2026-05-13.
Decidido · 2026-05-13
✓ Resolvido — #3 Falha de SMTP no registro: conta órfã
Sem rollback. Se SMTP falhar durante o registro, o user record é criado com email_confirmed=False aguardando. Tela "verifique seu e-mail" tem botão "Reenviar e-mail" que chama POST /api/auth/resend-confirmation. Erros de envio são loggados. Confirmado em 2026-05-13.
Decidido · 2026-05-13
✓ Resolvido — #4 Sem migração do usuário legado
Todos os usuários atuais criam conta nova. Seed do legado user/password permanece apenas em APP_ENV=development para testes locais. Em produção e staging, qualquer pessoa que queira acesso passa pelo fluxo normal de registro com e-mail. Sem caminho de auth especial. Confirmado em 2026-05-13.
Decidido · 2026-05-13
✓ Resolvido — #5 Rate limiting adiado
F1 entrega sem rate limit. Risco MED documentado na seção 05. Tempo de bcrypt cost 10 (~80ms) já limita parcialmente. Se aparecer abuso real em produção, reabrir como F1.1 com slowapi (~3h extras). Confirmado em 2026-05-13.
