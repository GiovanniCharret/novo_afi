04

Código-chave

Backend constrói WHERE incremental; q faz OR entre 4 colunas. Frontend tem uma regra que vale relembrar: ao mudar o contrato no dropdown, NÃO resetar os outros filtros — operador pode estar "passeando" entre contratos com o mesmo filtro de data.

backend/app/server.py — endpoint estendido
@app.get("/api/nf-entries")
def list_nf_entries(
    request: Request, db: DbSession,
    contrato_id: str | None = None,
    q: str | None = None,
    data_inicio: date | None = None,
    data_fim: date | None = None,
    valor_min: Decimal | None = None,
    valor_max: Decimal | None = None,
    tipo_nota: str | None = None,
):
    get_authenticated_user(request)
    stmt = select(NfEntry)

    if contrato_id:
        stmt = stmt.where(NfEntry.contrato_id == contrato_id)
    if q:
        like = f"%{q}%"
        stmt = stmt.where(or_(
            NfEntry.numero_nf.ilike(like),
            NfEntry.fornecedor.ilike(like),
            NfEntry.cnpj.ilike(like),
            NfEntry.descricao.ilike(like),
        ))
    if data_inicio:
        stmt = stmt.where(NfEntry.data_emissao >= data_inicio)
    if data_fim:
        stmt = stmt.where(NfEntry.data_emissao <= data_fim)
    if valor_min is not None:
        stmt = stmt.where(NfEntry.valor_total >= valor_min)
    if valor_max is not None:
        stmt = stmt.where(NfEntry.valor_total <= valor_max)
    if tipo_nota:
        stmt = stmt.where(NfEntry.tipo_nota == tipo_nota)

    rows = db.scalars(stmt.order_by(NfEntry.data_emissao.desc())).all()
    return [serialize_nf_entry(e) for e in rows]
frontend/src/components/NfsBrowser.jsx — soma client-side
function formatBRL(n) {
  return new Intl.NumberFormat("pt-BR", {
    style: "currency", currency: "BRL"
  }).format(n);
}

function NfsBrowser() {
  const [contratoId, setContratoId] = useState("");
  const [filters, setFilters] = useState({
    q: "", data_inicio: "", data_fim: "",
    valor_min: "", valor_max: "", tipo_nota: ""
  });
  const nfs = useDebouncedFetch("/api/nf-entries",
    { contrato_id: contratoId, ...filters });

  const soma = nfs.reduce(
    (acc, n) => acc + Number(parseBR(n.valor_total)), 0
  );

  if (!contratoId) return <EmptyState/>;
  return (
    <>
      <FilterBar filters={filters} onChange={setFilters} />
      <Table rows={nfs} />
      <Footer count={nfs.length} soma={formatBRL(soma)} />
    </>
  );
}
05

Riscos & mitigações

Risco
Sev
Mitigação
Estender GET /api/nf-entries com novos params quebra o consumidor existente em App.jsx (tabela principal pós-upload).
HIGH
Todos os params com default None. Sem param = WHERE vazio = lista completa, idêntica ao comportamento atual. Teste de regressão obrigatório.
NFs pré-F2 têm contrato_id = NULL. Filtrar por contrato esconde elas — comportamento esperado, mas pode surpreender o operador.
MED
No empty state, se contagem do contrato = 0, exibir hint: "Nenhuma NF encontrada. NFs anteriores à seleção de contrato (F2) podem não estar associadas." Não bloqueia entrega.
Soma client-side da coluna valor_total diverge da soma real se o frontend recebe a string formatada brasileira ("5.656,23") e parseia errado.
MED
Backend já serializa valor_total do raw_payload (string BR) ou do campo Decimal. Frontend usa helper parseBR dedicado. Teste: NF com valor "1.234,56" deve somar exato.
Dropdown de contratos carrega 110 entradas — sem busca interna, escolher contrato vira scroll demorado.
LOW
Em base de 110, <select> nativo aceita digitar pra pular pelo primeiro caractere. Suficiente. Se base crescer pra 1000+, trocar por combo searchable.
Filtro q com % ou _ literal vira wildcard de SQL LIKE.
LOW
Aceitável neste cenário — operadores não digitam esses chars em buscas reais. Se virar problema, escapar com str.replace antes do f"%{q}%".
